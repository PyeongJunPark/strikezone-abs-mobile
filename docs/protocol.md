# 스마트폰–노트북 통신 규격 v2 (단방향 버퍼 전송)

상태: 확정 초안 (2026-11-11)  
상세 설계 및 타임라인 근거: [링 버퍼 및 노트북 트리거 기반 아키텍처](buffer-trigger-architecture.md)

---

## 1. 개요 및 설계 원칙

- **단방향 비디오 전송 구조:** 
  스마트폰 앱의 구현 부담(UI, TTS, 수신 파서)을 없애기 위해, 판정 결과 역전송 과정을 생략하고 **노트북에서 판정 및 음성 출력을 직접 완결**합니다.
- **제어 방식:** 
  스마트폰은 상시 4.5초 링 버퍼를 유지하며, 노트북에서 `DUMP` 명령을 수신했을 때만 해당 비디오 바이너리를 스트리밍합니다.

---

## 2. 네트워크 및 연결 설정

- **프로토콜:** TCP Socket
- **포트:** 기본 `9999`
- **역할:**
  - 스마트폰: TCP 클라이언트 (앱 실행 시 노트북 IP:9999로 연결) 또는 서버 모드 가능 (기본 권장: 스마트폰이 서버 소켓 오픈, 노트북이 접속).
  - 노트북: 명령 송신자 및 비디오 수신자
- **네트워크 구성:**
  - 전용 무선 공유기 (5GHz 대역 권장, 외부 인터넷 연결 불필요)
  - 또는 스마트폰 모바일 핫스팟 (5GHz 대역 권장, 야외 필드용 간편 1:1 연결)
  - 또는 USB 테더링 유선 연결 (`adb forward tcp:9999 tcp:9999`)

---

## 3. 메시지 형식 및 패킷 구조

### 3.1 노트북 ➡️ 스마트폰 (트리거 제어 패킷)

- **형식:** ASCII 단문 텍스트 (줄바꿈 `\n` 종료)
- **명령어:**
  ```text
  DUMP 4.5\n
  ```
- **설명:**
  - `DUMP [초]`: 현재 시점 기준 직전 해당 시간(기본 4.5초)의 비디오 버퍼를 MP4 파일로 패키징하여 즉시 전송 요청.

### 3.2 스마트폰 ➡️ 노트북 (비디오 바이너리 스트림)

스마트폰은 `DUMP` 명령 수신 즉시 비디오 데이터의 전체 크기(4바이트)를 먼저 보낸 후 바이너리 데이터를 스트리밍합니다.

```text
+-----------------------------------+------------------------------------------+
|      Payload Length (4 Bytes)     |          MP4 Video Binary Data           |
|      (Big-Endian 32-bit uint)     |                (Length Bytes)            |
+-----------------------------------+------------------------------------------+
```

1. **Length (4 Bytes):** 전송할 MP4 파일의 총 바이트 수 ($N$, Big-Endian Unsigned 32-bit Integer).
2. **Video Payload ($N$ Bytes):** 스마트폰 하드웨어 인코더(MediaCodec)가 생성한 H.264/AAC MP4 바이너리 스트림.
3. 전송이 완료되어도 소켓 연결은 끊지 않고 유지(`keep-alive`)하여 다음 투구에 재사용합니다.

---

## 4. 예외 및 오류 처리

1. **소켓 연결 끊김:** 스마트폰 앱은 연결 단절 감지 시 2초 주기로 자동 재연결 시도.
2. **버퍼 부족 (앱 시작 직후 DUMP 수신):** 앱 실행 후 4.5초가 채 지나지 않아 DUMP 명령을 받은 경우, 현재까지 누적된 프레임(예: 2초)만이라도 패키징하여 전송하고 에러로 중단하지 않음.
3. **타임아웃:** 노트북은 `DUMP` 전송 후 3초 이내에 페이로드 수신이 시작되지 않으면 타임아웃 처리하고 연결 상태 재확인.
